INTRODUCTION

Design-to-Code for Employee Service

Design-to-Code is a way for product designers to work closer to production. With AI, more of the design process can now happen directly in code, and with tools like Cursor, Claude Code, or Codex, designers can turn product ideas into reusable code instead of relying mainly on static screens.

The result is an interactive prototype grounded in the target production repository, giving stakeholders something they can use and giving engineers reusable code and implementation context to carry into development.

Why Design-to-Code

Static designs are useful for exploring ideas, but they can leave important questions unanswered. How does the experience behave? What happens when there’s no data? Which states, interactions, and edge cases do we need to support? When all of those answers live in small annotations across a large set of Figma mocks, engineers are left navigating complex files, which increases ambiguity around the expected outcome. That’s without even mentioning the effort designers need to put in to make sure no important notes slip through the cracks.

An interactive prototype lets PMs and other stakeholders experience the product before it’s implemented. It makes conversations more concrete, helps teams spot technical gaps earlier, and gives everyone a clearer understanding of what needs to be built, especially engineers. And because your handoff becomes code, it speaks the same language as engineering.

Designers working with code add a new layer of value. When the work is grounded in the target production repository, it can use the right components, dependencies, patterns, and data shapes. Engineers can reuse what you create instead of starting from a static mock and translating everything into code from scratch.

What you create

Design-to-Code produces 2 connected outcomes:

  • An interactive experience that people can use, review, and discuss
  • Reusable code and implementation context that engineers can carry into development

The interactive experience helps people understand how the product works. The code gives engineers a clearer starting point for implementation by showing what they can reuse and what they still need to build.

How you create it

To help designers get started quickly, the design kit uses product shells. These are prebuilt templates that include the Zendesk navigation framework and page structure, without the size and complexity of full production repositories. This means you can focus on the feature you’re designing instead of rebuilding the whole page from scratch every time.

Shells are lightweight versions of the product pages designers work in most often. They come with pre-populated content and can evolve as teams use them in new projects. New shells can be added for other product areas, and existing ones can be updated to stay aligned with the real products.

Your work happens inside the <Main> area. The shell takes care of the Zendesk navigation and basic page structure, so what you build already looks and feels like Zendesk from the start.

Benefits

Design-to-Code gives you:

  • Speed: Start with a prebuilt product shell and focus on the feature you’re designing in seconds
  • Clarity: Give PMs and stakeholders an interactive experience they can use and discuss
  • Consistency: Keep your work aligned with Zendesk code, accessibility, and product standards
  • Reusable code: Give engineers code and implementation context they can carry into development
  • Shareable output: Share prototypes for reviews and team discussions

Who can use this

Design-to-Code brings product designers, PMs, and engineers onto the same page:

  • Product designers: Explore ideas, build interactions, and prepare reusable code
  • PMs and stakeholders: Experience the product and review decisions before implementation
  • Engineers: Review the work in code, understand the design decisions, and reuse what fits the production implementation
SETUP

Getting started

Set up a product shell and start a Design-to-Code project in 5 steps. You don’t need prior coding experience to follow this setup, but a basic understanding of terminal commands is recommended.

What you'll need

Before you start, make sure you have:

New to vibe coding?
These resources can help you get familiar with the tools and workflow: Cursor Enablement Program by Andrii Lytvynko, Vibes to Production by Abi Iyer, and GitHub 101 by Stephanie Quemena.
1

Clone the design kit

ONE TIME ONLY

Run these commands once:

Terminal
$mkdir -p ~/zendesk/design-kits ~/zendesk/prototypes
$cd ~/zendesk/design-kits
$git clone git@github.com:zendesk/employee-service-design-kit.git

Open Terminal, copy the commands, paste them, and press Enter. This creates the folders for your design kits and Design-to-Code projects, then downloads the Employee Service Design Kit.

You’ll use this folder structure for each project: ~/zendesk/prototypes.

Already cloned the design kit?

Get the latest product shells and skills before starting another project:

Terminal
$cd ~/zendesk/design-kits/employee-service-design-kit
$git pull
2

Create a project folder

Create a folder for your project.

Terminal
$mkdir ~/zendesk/prototypes/my-new-project

Replace my-new-project with a short name that describes the work. You can also create the folder in Finder inside zendesk/prototypes.

Each Design-to-Code project has its own folder.

3

Open the project

Open ~/zendesk/prototypes/my-new-project in the code editor or AI coding tool you plan to use.

In Cursor or VS Code:

  1. Select File → Open Folder
  2. Go to ~/zendesk/prototypes/my-new-project
  3. Select Open
4

Set up the product shell

Open the integrated terminal and run:

Terminal
$~/zendesk/design-kits/employee-service-design-kit/scripts/setup-here.sh

The setup will ask you to select a product shell. It then copies the shell into your project, installs its dependencies, and sets up Git. The process usually takes about 30 seconds.

If the setup stops because of an npm authentication error, go to Troubleshooting.

5

Preview your project

Run this command to start a local version of your project:

Terminal
$npm run dev
VITE v8.1.0 ready in 245 ms
➜ Local: http://localhost:5173/
➜ Network: use --host to expose

The command will give you a local URL, such as http://localhost:5173/. Open it in your tool’s browser, if available, or in your regular web browser.

The page updates automatically when your project files change, so you can review the experience as you build.

Your project is ready

Your product shell is now running. Your project includes:

  • A product shell with Zendesk navigation and page structure
  • Example content inside <Main> that you can replace
  • Design-to-Code skills you can use from your AI coding tool

Some product shells include pages from multiple Zendesk products. For example, a shell might include Admin Center and Support pages, with navigation between them. If your project only needs one product area, ask your AI coding tool to remove the pages, navigation interaction, and code for the other area. This keeps your project focused and easier to work with.

Ground your project

Running the product shell completes the setup, but your work isn’t grounded in production yet. Before you start building, use match-repo to give your AI coding tool context from the target production repository.

This context helps your project refer to the right components, versions, dependencies, patterns, and data shapes from the start. You don’t need to understand every technical detail it finds. Later, the handoff step adds the relevant context to HANDOFF.md, so engineers can clearly see what they can reuse and what still needs to be built.

Go to Design-to-Code to continue.

SKILLS

Skills

Skills are guided workflows that help your AI coding tool complete common Design-to-Code tasks. They can ground your project in a production repository, share your work, run quality checks, and prepare the engineering handoff.

The included skills currently work with Claude Code and Cursor. Use /name in Claude Code or @name in Cursor. You can still use other AI coding tools to work on your project, but these commands are currently available only in those two tools.

Design-to-Code workflow
match-repo

What it does

This skill grounds your project in the target production repository. It asks which product area and page you’re working on, then reads the repository’s current versions, dependencies, component patterns, and available GraphQL data.

It saves this context for your AI coding tool to use throughout the project. It also adds relevant repository details to the README when they’re available.

When to use

Run this after setting up your product shell and before building your feature. Run it again if the target repository or product area changes.

Invoke it

Claude Code
>/match-repo
Cursor
>@match-repo

What you get

Project context saved for the tool you’re using, such as .claude/target-context.md or .cursor/target-context.md. This file stays local and isn’t included when you share the project.

The relevant context is added to HANDOFF.md later, so engineers don’t need access to the local file.

publish

What it does

This skill shares your project for the first time. It creates a private GitHub repository, pushes your code, and sets up a live internal site that your team can use and review.

It also adds the project details, ownership information, status, and live link to the README.

When to use

Run this when you’re ready to share the experience with PMs, stakeholders, or engineers. Use it only the first time you share a project. For later changes, use publish-update.

Invoke it

Claude Code
>/publish
Cursor
>@publish

What you get

A private GitHub repository and a live link you can share with your team. The skill also sets up the deployment workflow and npm authentication needed to keep the site running.

publish-update

What it does

This skill updates a project you’ve already shared. It reads what changed, recommends a version update, adds a short summary to the README, and asks for confirmation before pushing the changes.

The live site rebuilds automatically after the update is pushed.

When to use

Run this whenever you’ve made changes worth sharing after using publish.

Invoke it

Claude Code
>/publish-update
Cursor
>@publish-update

What you get

An updated repo, a new entry in the README’s version history, and an updated live site.

repo-check

What it does

This skill checks whether the feature you’re designing still aligns with the target production repository. It compares the project against the context created by match-repo, including versions, dependencies, component APIs, and data structures.

It focuses only on the feature you identify. Product shell navigation, prebuilt pages, mock data, and other supporting code are excluded unless they’re part of the work you want engineers to reuse.

This is an alignment check, not a general code review, and it doesn’t determine whether the code is production-ready.

When to use

Run this when the solution is close to final and before preparing the engineering handoff. Run match-repo first so the skill knows which repository to compare against.

Invoke it

Claude Code
>/repo-check
Cursor
>@repo-check

What you get

A list showing what aligns with the target repository and what needs attention. Each gap includes the smallest change that would bring the project closer to the production implementation.

handoff

What it does

This skill prepares the project for engineering handoff. It reads the feature code and the context gathered throughout the project, then creates a self-contained HANDOFF.md.

The file explains:

  • What engineers can reuse
  • Which parts only support the interactive experience
  • How the feature is expected to connect to production data
  • Which versions and dependencies engineers need to consider
  • The intended behavior, states, decisions, and open questions
  • What engineers still need to build

The skill preserves notes already added to HANDOFF.md and updates the file instead of replacing your work.

When to use

Run this when the experience, content, and quality checks are complete. Before starting the handoff, run repo-check, localize, and a11y-check.

Invoke it

Claude Code
>/handoff
Cursor
>@handoff

What you get

One HANDOFF.md based on the actual project code. It separates reusable feature work from product shell code, mock data, and other parts that exist only to support the interactive experience.

The skill also marks the README as Ready for development and checks that the project builds successfully. This status means the Design-to-Code work is ready for engineering review. It doesn’t mean the code is production-ready.

Localization
localize

What it does

This skill prepares the final product content for Zendesk’s translation process. You identify the feature or page to review, and the skill finds its user-facing content while filtering out technical strings and product shell content.

You choose which strings need translation. The skill then creates and validates an i18n/en-us.yml file with the product content and context translators need.

When to use

Run this when the product content is close to final, after reviewing it with product, engineering, and content design. If the content changes later, use localize-update.

Invoke it

Claude Code
>/localize
Cursor
>@localize

What you'll do

1

Tell the skill which feature, component, or page contains the final content

2

Review the user-facing strings it finds

3

Choose which strings need translation

4

Review the generated localization file and its translator descriptions

5

Confirm whether to commit and push the file

What you get

An i18n/en-us.yml file containing the selected product content and translator descriptions:

i18n/en-us.yml
title: "PLACEHOLDER_FILE_TITLE"
packages:
  - PLACEHOLDER_PACKAGE

parts:
  - translation:
      key: "txt.PLACEHOLDER.0001"
      title: "Drawer title - Noun phrase - Heading of the edit-columns drawer."
      value: "Edit columns"
      screenshot: "PLACEHOLDER_SCREENSHOT"

What the engineer finalizes

The engineer adds the repository-specific information that the Design-to-Code project can’t determine:

  • The Rosetta package name
  • Final translation keys
  • Screenshots using the final keys
  • Any repository-specific file information
Placeholder Who fills it Why
PLACEHOLDER_FILE_TITLE Engineer Document title, per team convention
PLACEHOLDER_PACKAGE Engineer Real Rosetta package name
txt.PLACEHOLDER.NNNN Engineer Key naming varies by team
PLACEHOLDER_SCREENSHOT Engineer Screenshot captured & named after the final key

The product content, translator descriptions, formatting, pluralization, and interpolation are prepared for engineers to carry into the repository’s localization workflow.

localize-update

What it does

This skill updates product content that was already prepared with localize. It changes the selected values while preserving existing keys, translator descriptions, and file structure.

The skill shows what it matched before making changes and asks for confirmation before updating the file.

When to use

Run this whenever the product content changes after you’ve used localize.

Invoke it

Claude Code
>/localize-update
Cursor
>@localize-update

What you'll do

1

Tell the skill which component changed or provide the old and new text

2

Review and confirm the matching localization entry

3

Update and validate the content, then choose whether to push the changes

Any screenshots containing the changed content need to be captured again after the text is final.

Accessibility
a11y-explore

What it does

This skill helps you make accessible design decisions while you build. It considers what an interaction needs to do, recommends the appropriate Garden or Flora component, and explains the effect of that choice on keyboard, screen reader, and other users.

The skill provides guidance only. It doesn’t edit your code.

When to use

Run this while exploring an interaction, selecting a component, or deciding how something should behave. Using it throughout the project helps you consider accessibility before the experience is complete.

Invoke it

Claude Code
>/a11y-explore
Cursor
>@a11y-explore

What you get

A recommendation based on the intended behavior, including relevant accessibility requirements and tradeoffs. The skill doesn’t create or change any files.

a11y-check

What it does

This skill reviews a feature, component, or interaction against WCAG 2.2 AA. You choose what to review, so it focuses on your work instead of checking the entire product shell.

It groups its findings as Critical, Major, or Minor, explains how each issue affects users, and proposes a fix. It changes the code only after you approve the individual fixes.

After applying the approved changes, the skill checks that the project still builds successfully. It also identifies anything that needs manual testing in the browser, with a keyboard, or with a screen reader.

When to use

Run this when the content and behavior are close to final. Run it again after making substantial changes to the feature.

Invoke it

Claude Code
>/a11y-check
Cursor
>@a11y-check

What you get

A plain-language accessibility review and the fixes you approve. Any behavior that can’t be confirmed from the code is clearly marked for manual testing.

PROCESS

Design-to-Code

Design-to-Code starts once your product shell is running. This workflow helps you ground your project in the target production repository, build and review the experience, share it with your team, and prepare reusable code and implementation context for engineers.

Connect MCP servers

MCP servers give your AI coding tool access to the Zendesk context it needs while you work. You can connect them through the AI Gateway.

You may not need every server for every project. However, connecting all of them is recommended so your AI coding tool can use the right context whenever the work requires it.

Work in the tools that fit your project

Design-to-Code isn’t tied to one AI coding tool. You can work in Cursor, VS Code, Codex, Claude Code, or another tool that supports your preferred workflow. You can also move between tools when one is better suited to a particular task.

Avoid working in the same project directory with two AI coding tools at the same time. They may edit the same files, overwrite changes, or create conflicting instructions.

1

Ground your project

Before you start building, run match-repo. This gives your AI coding tool context from the target production repository, including the versions, dependencies, components, patterns, and data structures used by the engineering team.

The skill saves what it finds as project context that your AI coding tool can refer to throughout the project. The exact format and location depend on the tool you’re using.

Grounding your project doesn’t copy the production repository into your product shell. It gives your AI coding tool enough information to make decisions that are better aligned with the code engineers already use.

2

Build and iterate

The first result is only a starting point. Continue making design decisions, testing, and refining the experience.

Keep the local preview open while you work. Review each change in the browser, try the interactions, and update your instructions when something doesn’t work as expected.

Use a11y-explore as you build new components and interactions. It can help you consider accessibility from the beginning instead of waiting until the end to review the full experience.

Because your project is connected to the GitHub MCP server, you can also ask your AI coding tool to search production repositories for common patterns or similar solutions. This can help you understand how Zendesk already solves related problems and improve the reusable code you prepare for engineers.

Be specific about what you’re building and ask your AI coding tool to focus on that part of the experience. Define this focus from the beginning so the feature code and handoff stay clear. This also helps separate reusable work from navigation components, prebuilt pages, mock data, and other parts of the product shell that support the interactive experience but aren’t intended for the production repository.

3

Share and update your work

When you’re ready to share the experience with PMs, stakeholders, or engineers, run publish. This creates a private GitHub repository and a live internal site that your team can use and review.

After making changes, run publish-update to update the repository and live site. This keeps the shared experience aligned with your latest work.

4

Run quality checks

Run the quality checks when the content and solution are close to final:

  • Repository alignment: Run repo-check to find differences between your project and the target production repository
  • Localization: Run localize to prepare the final product content for Zendesk’s translation process
  • Accessibility: Run a11y-check to review the completed components and interactions against Zendesk accessibility standards

If the product content changes after running localize, use localize-update to update the localization files.

5

Prepare the engineering handoff

When the work is ready for engineers, run handoff. The skill reads your project and creates a HANDOFF.md file explaining what engineers can reuse, which parts only support the interactive experience, and what still needs to be connected or built in production.

Ask your AI coding tool to capture every relevant note in HANDOFF.md, including the decisions and annotations you would usually add to your Figma files. Engineers should be able to understand the work from this file, so review it carefully and make sure it covers the intended behavior, states, design decisions, reusable code, production connections, and open questions.

This gives engineers a clearer starting point than static Figma designs and annotations alone.

Next: Design-to-Production

The outcome of Design-to-Code is not production-ready code. It’s a streamlined way for designers to work closer to code, reduce ambiguity, and prepare a stronger handoff for engineering. Engineers still decide what can be reused and complete the work required by the production repository.

Design-to-Production is a separate, more advanced path where designers contribute directly to production repositories, submit PRs, and follow the same development process as engineers while using AI tools to help write the code. It requires deeper technical knowledge, and the process varies across repositories and teams. Guidance for Design-to-Production is coming soon.

HELP

Troubleshooting

If something stops you from setting up or working on a Design-to-Code project, start with the fixes below. Keep the full error message available so you can use it to understand what went wrong or ask for help.

npm authentication error

If the product shell setup stops while installing dependencies and the terminal shows an npm authentication error, connect your machine to Zendesk’s npm registry. You usually need to do this only once per machine.

1

Add the Zendesk registries to ~/.npmrc

~/.npmrc
@zendesk:registry=https://zdrepo.jfrog.io/artifactory/api/npm/npm/
@zendesk-ui:registry=https://zdrepo.jfrog.io/artifactory/api/npm/npm/

Open ~/.npmrc and add both lines. If the file doesn’t exist, create it in your home directory.

2

Sign in to both registries

Terminal
$npm login --registry=https://zdrepo.jfrog.io/artifactory/api/npm/npm/ --scope=@zendesk
$npm login --registry=https://zdrepo.jfrog.io/artifactory/api/npm/npm/ --scope=@zendesk-ui

Follow the prompts using your Zendesk credentials. When both commands finish, run the product shell setup again.
